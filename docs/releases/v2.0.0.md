## Summary

TaskFlow v2.0 modernizes the four-stage workflow board while retaining its
frontend-only React/TypeScript identity and supported v1.x data. The release adds
a warm clay visual system, responsive board/details experience, explicit state
boundaries, independent Manual ordering, capacity enforcement and stronger
versioned browser persistence.

## Highlights

- Semantic design tokens, shared interface primitives and a responsive application
  shell establish consistent controls, colors, spacing, focus and motion.
- Compact Kanban cards display Category then Priority, related-work context and
  parent progress. Headers show complete-board capacity. Pointer/touch drop
  previews and keyboard movement share validation and meaningful focus recovery.
- Read-first desktop drawers/mobile sheets separate viewing from editing. Forms
  have consistent metadata order, compact footer actions, linked parent context,
  collapsible subtasks, associated errors and protected dirty-draft dismissal.
- Search, Category/Priority/Status filters, active chips, clear-all, result counts
  and zero-result recovery make board scope explicit. Mobile uses a filter sheet
  and single-stage navigation, including short touch landscape layouts.
- Priority retains stable arrival ties; optional Manual stores separate positions.
  Unfiltered users can reorder by drop placement or named actions. The selected
  mode persists independently of task data; filtering preserves hidden order.
- Fixed capacity limits enforce five In Progress and three In Review tasks using
  full-board membership. Over-limit legacy boards restore without discarding work;
  valid exits remain possible while further arrivals are blocked.
- Strict types, intention-specific immutable reducer actions and shared selectors
  separate UI, complete domain state, presentation choices and persistence.
  Invalid content/movement/relationship/order operations remain atomic.
- Board schema 3 adds explicit nullable manual positions and supported migration.
  Separate preference schema 1 stores the mode. Invalid, incompatible and
  conflicted storage has typed saving-paused recovery and confirmed repair/replacement.
- Accessibility work strengthens control names/targets, modal focus isolation and
  return, keyboard continuation, live feedback, reduced motion and enlarged text/
  zoom behavior. This is scoped verification, not full WCAG certification.

## Upgrade and storage notes

Application version **2.0.0**, board schema **3**, and preference schema **1** are
independent version numbers. Board data remains at `taskflow-board`; the selected
ordering mode uses `taskflow-view-preferences`. No server/database is introduced.

Supported paths: unversioned v0 → v1 → v2 → v3; schema 1 → v2 → v3;
v1.5/schema 2 → v3. Legacy checklist conversion retains identities/titles and
completion through linked child tasks. Schema-2-to-3 preserves valid content,
relationships, timestamps, arrival ties and saved manual lists. Absent positions
become uninitialized `null`, not automatically generated Manual order. Existing
schema-2 checklist fields are preserved rather than reconverted. Current schema-3
loads do not rewrite; repeated conversions do not duplicate children.

Validation constructs the whole trusted result before writeback. Failed decoding/
conversion and unknown future versions preserve the original bytes and pause
saving. Damaged order restores safe core data in Priority and requires confirmed
repair. Read errors, failed saves and other-tab changes offer explicit recovery.
Confirmed replacement is destructive; dismissal alone does not resolve a saving
restriction. No separate migration backup or automatic downgrade is provided.
Older readers may reject schema 3, so do not assume reverting application code
also converts a board back to an older schema.

Storage is browser/profile/origin-specific. Preview/staging/production and
localhost ports do not share saved boards. LocalStorage has no compare-and-swap
transaction or cross-tab merge; postflight failure can occur after a complete
write. Keep local work open until retry/recovery is resolved. See
[migration](../v2-data-migration.md) and [recovery](../v2-persistence-recovery.md).

## Verification

Merged [#49 technical QA](../v2-performance-regression.md) records **487 unit/
component/integration tests**, **70 Chromium cases**, **60 selected Firefox/WebKit
cases**, nine focused recovery repetitions and 17 practical regression checks.
It covers supported migrations, retained originals, workflow/capacity/order,
relationships, responsive viewports, keyboard/focus/announcements, axe scans,

Lighthouse medians (Performance/Accessibility/Best Practices/SEO): mobile
**99/100/96/82**, desktop **100/100/96/82**, from three valid runs per profile.
Production JS **327.18KB / 99.73KB gzip** and CSS **48.93KB / 8.36KB gzip** build
without warnings. Representative 20/100/300-task results meet observed targets
on an off-reference Intel Mac; they do not certify the approved M1 reference host
or real-user/network performance. The report retains ranges, outliers and tool/
hardware settings rather than selecting best runs. No broad optimization was justified.

Release-branch checks and exact-origin staging/production results belong in the
[release record](../v2-release-checklist.md). Technical QA and a green deployment
status do not establish that an untested production origin is verified.

## Known limitations and non-goals

Physical iOS/Android/on-screen keyboards, actual Safari and spoken VoiceOver
remain separate owner checks. Automated scans cannot certify every interaction.
The local QA record retains the Speed Insights script404, missing meta description
and robots SPA fallback findings; verify deployed analytics/routing/indexing
behavior during release review rather than suppressing audits.

This remains a single-user frontend application. Backend/database servers,
authentication, SaaS accounts, teams/collaboration, AI task generation or
prioritization, due dates, import/export, cloud sync and configurable capacities
are not included. Search/filters and unsaved forms reset on remount; only the
approved ordering preference persists.
