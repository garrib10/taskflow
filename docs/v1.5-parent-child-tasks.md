# Linked parent and child tasks

The approved product decisions live in [issue #60](https://github.com/garrib10/taskflow/issues/60). Relationships have one level. Children are independent task records in the existing board columns, with their own ID, title, description, priority, category, status, and creation date. The application's existing update metadata remains the board's `lastUpdated`, supplied in each action. No duplicated child arrays or recursive task objects are stored.

## Model and operations

Only a child stores `parentId?: Task["id"]`. Absence means an independent task; a task with linked children is a parent. Full-board selectors derive parent context, children, and completed/total progress, even when search or filters hide related cards. Ambiguous IDs do not resolve as valid parents.

`TaskEdits` still permits only title, description, priority, and category. IDs, creation metadata, workflow status, legacy checklist data, and relationships remain reducer-managed. Explicit field merging preserves relationships even when an old edit snapshot contains additional keys.

Three narrowly typed actions manage relationships:

- `CREATE_CHILD_TASK` carries a supplied new task and an existing parent ID. New children start in To Do. The reducer creates the task and link together.
- `SET_PARENT` carries an existing task ID and a parent ID, or `null` for detachment. Attaching, reassignment, and detachment preserve all other task data.
- `DELETE_PARENT_TASK` represents explicit approval to delete only the parent and detach its children as independent tasks. Ordinary `DELETE_TASK` cannot delete a parent with children.

Every action supplies `updatedAt`; IDs and clocks are read before dispatch. Domain validation returns a typed error code and message. Board uses that result for the existing error notification, and forms remain open on validation failure. The reducer repeats validation against its current state before mutation; invalid actions return the original board and timestamp.

Validation rejects self-parenting, cycles, missing or ambiguous IDs, duplicate task creation, unchanged links, and deeper nesting. A child cannot become a parent; a task with children cannot become a child. Detachment can remove an invalid legacy link without deleting the task; full hydration validation and recovery remain separate work.

## Completion and deletion

The existing forward-only workflow remains To Do → In Progress → In Review → Done. Each child moves independently. A parent may advance through the first stages while children remain unfinished, but completion is rejected until every linked child is Done. The error names the blocking work using the full board.

The existing workflow rejects reopening both parents and children. No reverse transition is added by this feature. Completed parents cannot receive newly created or unfinished children, including through reassignment. Completed children may be reassigned to an eligible completed parent, detached, edited, or deleted without changing their status.

Parent deletion presents a relationship-aware confirmation: **Delete Parent and Detach Children**. Cancellation preserves all tasks; confirmation removes only the parent and detaches every current linked child atomically. Users may instead detach or reassign children individually through Manage Parent before ordinary parent deletion. Child deletion removes only that child, and progress is recalculated rather than separately updated.

## Board presentation

Parent cards show a compact completed/total count, segmented blue progress bar with one segment per subtask, and rounded percentage. Subtask cards show ordinary task content and actions; parent context and relationship controls appear only in the editor. Linked children are called subtasks in the task editor. Open an unfinished task's Edit form and use **Add SubTask**. With no subtasks, only the button appears; after the first is created, the Subtasks section appears. Completed tasks offer no creation button. The section shows completed/total progress and rows ordered by creation date (oldest first), with blue outlined circles for unfinished subtasks, blue circles with white checkmarks for completed subtasks, and clickable titles, without status text or separate Edit buttons, following the issue/sub-issue pattern in #39. Creation uses the existing form with parent context and inherited priority/category defaults. Subtasks remain independent cards on the board.

Adding or editing a subtask from the parent editor returns to that editor. The parent's unsaved title, description, priority, and category stay intact while the subtask saves independently. Cancelling the parent draft does not undo a saved subtask. Subtask editors show workflow status and a bordered Parent pill with a status icon and clickable parent title; navigation prompts before discarding unsaved subtask edits. A subtask cannot add another subtask, preserving one-level relationships.

Manage Parent is available inside eligible task editors and opens a separate form for selecting an eligible parent or becoming independent. The task draft stays intact when relationship management closes, and relationship changes save independently. Subtask cards retain ordinary editing, deletion, and drag handles. All board titles open their task editor and turn blue with an underline on hover or keyboard focus. Pointer dragging starts after six pixels of movement so title clicks remain available. Opening a related task uses its editor and preserves board search/filters.

Search and filters evaluate tasks independently. Parent context and child progress come from the complete board, not the visible subset. Native buttons, select controls, and details/summary keep relationship controls usable with a keyboard. Child and relationship forms scroll within the viewport at narrow widths.

## Legacy checklist and persistence boundary

Unversioned and version 1 persisted checklists now migrate to linked child tasks through the [versioned persistence boundary](v1.5-persistence-reliability.md). Valid unique entry IDs/titles and parent data are retained; completed items become Done and unfinished items become To Do, inheriting parent priority/category and creation time with an empty description. Migration rejects malformed/conflicting entries or invalid completed-parent relationships without overwriting the original. Repeating migration does not add duplicate children.

The domain's `subtasks` field and existing checklist reducer actions remain for compatibility. Current-version checklist fields, if present, are validated and preserved. Existing entries remain visible in a labeled Legacy checklist section; new UI creation uses linked subtasks. Legacy entries do not count toward linked-child progress until converted.

Schema version 2 uses an explicit envelope and revision metadata. Storage errors and rejected data preserve in-memory work, show a message, and follow the documented recovery/conflict policy. Import/export, broader notification expansion, capacity limits, CSS restructuring and backend work remain deferred.

## Verification

Regression coverage includes one-level resolution and progress; invalid relationships; atomic creation, reassignment, detachment and deletion; stale editing; completion restrictions; deterministic replay; filtered context; keyboard controls; relationship-aware confirmations; error messages; legacy preservation; and a save/load round trip. Board interaction tests isolate the drag adapter because jsdom has no layout. Real pointer movement is checked separately in the browser. Existing workflow, priority, filtering, reducer, and notification tests remain intact.
