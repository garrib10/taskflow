# v1.5 state safety contracts

Both application and tooling TypeScript configurations enable `strict`. `Task.description` is required, including through the `Board` type used by persistence. Task creation, form validation, edits, sample data, and test fixtures agree on that contract. Required `string` typing does not itself enforce nonempty text: the form continues to validate trimmed descriptions.

`taskStatuses` is the single source for the four workflow statuses and their union type. The status guard accepts unknown inputs and narrows only supported values. Workflow rules and drag destinations use the guard before lookup or dispatch. The existing forward-only workflow remains To Do → In Progress → In Review → Done.

The exported domain reducer retains the existing `useReducer` architecture; the hook loads and saves the board. UI handlers generate dates and task/checklist IDs before dispatch. Every action carries `updatedAt`; creation actions carry the complete newly created entity. The reducer never reads the clock or generates an ID, so replaying the same state and action produces the same result.

Movement checks the source task, unambiguous identity, destination column, source consistency, and workflow before constructing a new board. Failed operations return the original board object and retain its timestamp. Successful moves remove exactly one source task and append exactly one destination task. Operations use the full board; filtered columns are presentation data only.

`TaskEdits` uses `Pick<Task, "title" | "description" | "priority" | "category">`. Editing merges those four fields into the current task. IDs, status, creation date, and checklist data stay under reducer control. This prevents an old edit form from erasing newer checklist changes. Because TypeScript structural typing allows variables with extra properties, the merge explicitly names allowed fields rather than spreading the edit payload.

Search and filter logic is exported as a pure domain function. Reset defaults are shared with the board's reset handler. Filtering does not mutate the underlying board or control workflow validation.

## Persistence compatibility and deferred scope

Runtime LocalStorage parsing, schema validation, versioning, migration, and recovery remain in #64–#67. The existing JSON assertion in `loadBoard` does not validate stored descriptions or dates. Legacy saved tasks may lack descriptions despite the stronger compile-time contract; the existing display, search, and form fallbacks remain until persistence compatibility is implemented. No migration or storage format change is introduced here.

Parent/child relationships (#61–#63), capacity limits, notification expansion, CSS, UI redesign, accessibility work, import/export, and backend functionality are outside this change. Capacity limits remain outside v1.5. The previously reported seven high npm audit advisories are unchanged; dependency remediation belongs to separate work.
