# Persistence reliability

## Confirmed baseline

Local develop matched origin. `npm install` exited 0, up to date, auditing 277 packages; it reported 7 existing high advisories and the existing optional fsevents allowScripts warning. Baseline: 119 tests across 8 files passed in 30.58 s. Typecheck and lint exited 0. Build exited 0: 46 modules, 874 ms; JS 261.35 kB / gzip 81.27, CSS 17.47 / gzip 3.90, HTML 0.45 / gzip 0.29. Branch `refactor/v1.5-persistence-reliability` was published before implementation.

Previously `useBoardReducer` called `loadBoard()` on every render, selected sample data for every failed load, and wrote the board after initialization. The only key was `taskflow-board`. Loading asserted parsed JSON was a Board, accepted malformed union values/dates/relationships, and restored dates without full validation. JSON/shape errors returned null and could be overwritten by sample data. Storage reads and writes could throw; failed writes were not visible. There was no schema, revision, or storage listener: independently edited tabs could overwrite each other silently.

TypeScript types disappear at runtime. They describe trusted application values but cannot verify JSON written by older code, another tab, a browser extension, or manually edited storage.

## Boundary and format

`src/persistence/validation.ts` parses unknown structure into trusted domain values. It validates board/columns, unique workflow columns and task IDs, required task fields, allowed status/priority/category, column/status pairing, canonical ISO UTC timestamps, checklist shape and identity, and one-level parent/child integrity using the domain validator. Current data must include all four columns. It rejects orphan/self/cyclic/deep links and unfinished children under Done parents.

`src/utils/storage.ts` is the only browser storage boundary. Current schema version is **2**:

```json
{"schemaVersion":2,"revision":"unique-write-id","board":{"id":"board-1","name":"TaskFlow Board","lastUpdated":"2026-01-01T00:00:00.000Z","columns":[{"id":"todo","title":"To Do","tasks":[]},{"id":"in-progress","title":"In Progress","tasks":[]},{"id":"in-review","title":"In Review","tasks":[]},{"id":"done","title":"Done","tasks":[]}]}}
```

Persisted dates are strings; validation constructs domain Dates only after checking them. JSON is parsed as unknown, never asserted to Board/Task. Revisions are independent of board.lastUpdated and are generated per successful write attempt; clocks do not determine conflicts.

Typed loads distinguish missing, current, migrated, future, invalid, migration-failed, and unavailable. Typed saves distinguish saved, conflict, unavailable, save-failed, and invalid-board. Read access, parsing, serialization, quota/security restrictions and writes are caught at the boundary. Saving validates serialized live data and checks the original raw value before writing. A caller cannot overwrite invalid/future data merely by passing its raw value.

## Migration paths and policy

Supported paths: unversioned **v0 → v1 → v2**, explicit **v1 → v2**, and direct current **v2** loading without migration. No other older versions are claimed. Invalid version values are rejected; versions above 2 are preserved without assuming compatible board structure.

- v0 → v1 validates legacy data, restores missing workflow columns, defaults absent legacy descriptions to an empty string and absent checklists to an empty array. Missing board.lastUpdated becomes the latest valid task creation date, or Unix epoch for an empty board. Existing timestamps, column titles, task data, and linked relationships remain intact. Invalid existing fields are not replaced with defaults.
- v1 → v2 converts each valid checklist into a linked child. Preserve the valid unique entry ID and title; parentId is the original task ID. Completed becomes Done, incomplete becomes To Do. Inherit parent priority/category, use an empty description and the parent's creation date. Parent fields/status remain unchanged. No random IDs or current-time timestamps are used during migration.
- Already linked children with the same checklist ID and same parent are reused with all their current fields/status preserved. Other collisions, duplicate/malformed entries, unsupported depth, or a completed parent with unfinished legacy work reject the whole migration. The recovery policy does not reopen completed parents or detach/drop work to manufacture a valid board.
- Validate each version step and the final linked board. Clear obsolete checklist entries only in the successful converted object. The decoder never writes. Save the complete converted board atomically only after successful validation and a stale-value check. A failed migration or failed write leaves the original stored value intact; repeating migration yields the same identities/content.

The current domain still supports legacy checklist reducer actions for compatibility. Current-schema validation therefore checks any remaining checklist fields; current-schema loading does not perform a surprise transformation. The historical round-trip regression still verifies those records are preserved. Ordinary UI creation uses linked tasks. Persisted historical v0/v1 checklists are converted.

## Recovery and save failures

Only a genuinely missing value initializes the sample board. Rejected/future/unavailable data initializes an empty in-memory workspace with a persistent saving-paused message. It never writes sample data over the original. No backup keys or unlimited recovery history are created: the original remains at the primary key.

The user may continue editing in memory but is told that work is not being saved and may be lost on closing. Write failures expose Retry saving, retain all reducer state, and never claim a successful persistence operation. Reload saved board requires confirmation before discarding the local in-memory work. Reload does not clear or replace stored data. Invalid/future recovery requires repairing the saved content or using a compatible version before reloading; import/export and reset features remain out of scope.

`useBoardReducer` hydrates once per mount. A PersistenceSession tracks the known stored value and persistence state; useSyncExternalStore delivers notices. Existing current data is not rewritten on mount, including React StrictMode's repeated effects. Migrated data is saved once; duplicate effects do not generate another revision. Existing success/error notification styles and confirmation controls are reused, with a persistent recovery message and actions.

## Multiple-tab policy

No automatic merging or automatic adoption. Storage events for other keys/storage areas are ignored; clear/removal events are relevant. Identical known raw content (including its revision) is ignored. Reusing a revision with different content is a conflict. External values are decoded and validated before classification; malformed external data is never dispatched to the reducer.

A different external board or removal pauses saves, retains the current in-memory work, and requests a confirmed reload. Reload explicitly discards local work and hydrates the latest stored data. Listener cleanup prevents subscriptions surviving unmount; external events do not write back, avoiding loops.

Every save also re-reads the current stored bytes before writing. A mismatch blocks the stale write even if a storage event was missed or delayed. A post-write check catches observable concurrent replacement. LocalStorage has no atomic compare-and-swap: two writes that interleave between preflight and write can still race. This policy improves ordinary tab safety without claiming transactional or collaborative guarantees. Revisions plus exact stored-byte comparison provide deterministic detection; timestamps alone are not reliable. Strong cross-tab transactions, backend persistence and real-time collaboration are deferred.
